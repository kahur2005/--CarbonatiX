# Data provenance: price history used for forecasting

**Status as of 2026-08-04: every price in this pipeline is SYNTHETIC.**
Nothing in `ml/data/price_history_SYNTHETIC.csv`, and nothing in the two
`_SYNTHETIC.pkl` model artifacts derived from it, is real market data.

## What is synthetic

- `ml/data/price_history_SYNTHETIC.csv` -- the entire file. Both the
  `lme_usd_per_ton` and `idx_carbon_idr_per_ton` columns are generated by
  a seeded random process, not observed from any market.
- `carbonatix/backend/app/forecasting/artifacts/nickel_lme_SYNTHETIC.pkl`
  -- a Prophet model fit to the synthetic nickel column above.
- `carbonatix/backend/app/forecasting/artifacts/idx_carbon_SYNTHETIC.pkl`
  -- a Prophet model fit to the synthetic IDX Carbon column above.

## Why

The task brief for this step asked for real LME nickel settlement prices
and real IDX Carbon daily prices (from
`https://www.idxcarbon.co.id/data-daily`). At build time this project had
no licensed data feed, no scraping arrangement, and no other reliable way
to obtain a clean, attributable daily series for either market within the
time available. Rather than leave the forecasting pipeline (Task 11,
which loads these artifacts to serve forecasts; Tasks 9 and 14, which
depend on Task 11) unbuilt, or -- much worse -- fabricate a series and
present it as real, we generated a clearly-labelled placeholder so the
rest of the pipeline can be built, exercised, and demoed end to end, with
every artifact self-evidently marked as not real.

This is a deliberate, ruled decision, not an oversight: fabricated data
presented as real would destroy the credibility of this project's results
at the first question from anyone who checked. A `_SYNTHETIC` suffix on
every filename that carries or derives from this data, comment headers in
the CSV, and stderr warnings in every script that touches it, all exist
so that no one -- including someone who encounters a single file with no
other context -- can mistake this for a real market series.

## How the synthetic series was generated

See the module docstring of `ml/generate_synthetic_prices.py` for the
full methodology. In summary:

- **`lme_usd_per_ton`**: a mean-reverting random walk (daily steps,
  weekdays only) anchored around USD 16,000/t with ~1.8% daily relative
  volatility, meant to be a plausible-shaped path for a liquid base-metal
  market -- not a prediction of where nickel will actually trade.
- **`idx_carbon_idr_per_ton`**: a slower-moving latent random walk
  anchored around IDR 45,000/t, revealed on only ~15-25% of weekdays to
  reflect that IDX Carbon (launched September 2023) is thin and trades
  sparsely. This was the column most important to get structurally
  right: a smooth daily carbon series would misrepresent the market and
  would let Prophet fit apparent seasonality that doesn't exist in a real
  thin exchange.
- The whole file is generated by a single seeded `numpy.random.default_rng`
  instance consumed in a fixed order, so re-running the generator produces
  a byte-identical CSV. This was verified: two independent runs of
  `python ml/generate_synthetic_prices.py` produced files with the same
  SHA-256 hash.

## Why there is no backtest / accuracy metric anywhere in `ml/`

Deliberately, and by ruling, this repository does not report a MAPE (or
any other accuracy metric) for either model. Fitting Prophet to a
synthetic series and then measuring error against that same synthetic
process measures how well Prophet recovered the generator's own random
walk -- it says nothing about forecasting skill on real nickel or real
IDX Carbon prices. A MAPE computed this way would be a number about our
random-number generator wearing a costume. Reporting it anywhere -- in a
markdown file, in a demo, in a slide -- would invite exactly the kind of
"can you quote your backtest accuracy" question this project cannot
honestly answer yet, and the honest answer ("we haven't backtested
against real data because we don't have real data") is a better answer
than a synthetic-vs-synthetic number that only looks like an answer.

Backtesting is deferred until Step "replace with real data" below is
done. Once real prices are in place, backtest properly: hold out the
last 30 days, refit on the remainder, compute MAPE against the held-out
real observations, and record it here or in a successor to this file.

## Provenance marker embedded in the pickles

The filename `_SYNTHETIC` suffix is not the only marker: a filename can be
lost if an artifact is copied or renamed (for example by a deploy step
that normalises artifact names, or by a later task "fixing" what looks
like a broken path). To survive that, both training scripts attach a
provenance record directly to the fitted `Prophet` object before pickling
it, under the attribute name **`carbonatix_provenance`** (identical in
`ml/train_nickel.py` and `ml/train_carbon.py` -- do not let the two
scripts diverge on this name, since Task 11 reads it by name from either
artifact):

```python
model.carbonatix_provenance = {
    "synthetic": True,
    "generated_on": "2026-08-04",
    "generator": "ml/generate_synthetic_prices.py",
    "seed": 20260804,
    "source_csv": "ml/data/price_history_SYNTHETIC.csv",
    "warning": "SYNTHETIC DATA - NOT REAL MARKET PRICES. Must be replaced "
    "before any published result or presentation. See "
    "ml/DATA_PROVENANCE.md",
}
```

This survives `pickle.dumps`/`pickle.loads` as a plain attribute on the
model instance -- verified by round-tripping both artifacts through
`pickle.loads` and asserting `model.carbonatix_provenance["synthetic"] is
True` (see `task-10-report.md` for the output). Task 11 can and should
read `model.carbonatix_provenance` when it loads these artifacts and
surface a synthetic flag in whatever it serves.

**When real data replaces this series**, `carbonatix_provenance` must be
updated or removed from the newly-trained model, not left in place still
claiming `synthetic: True`. The cleanest approach is for the real-data
version of the training scripts to simply not set the attribute at all
(so `getattr(model, "carbonatix_provenance", None)` is `None`/absent),
or to set `"synthetic": False` explicitly if a positive real-data marker
is useful downstream.

## What must be swapped in, and where

Before any forecast, demo, or published result from this project is
presented as real:

1. Obtain real daily LME nickel settlement prices (24 months minimum) and
   real IDX Carbon daily prices (every available print since September
   2023, from `https://www.idxcarbon.co.id/data-daily` or an equivalent
   licensed source).
2. Replace `ml/data/price_history_SYNTHETIC.csv` with a file built from
   that real data. Rename it to `ml/data/price_history.csv` (drop the
   `_SYNTHETIC` marker -- the marker exists precisely so that a renamed,
   real file is visibly different from this one).
3. Update `ml/train_nickel.py` and `ml/train_carbon.py`:
   - `SOURCE` should point at the new `price_history.csv`.
   - `OUT` should point at `nickel_lme.pkl` / `idx_carbon.pkl` (drop the
     `_SYNTHETIC` suffix).
   - Remove the "TRAINED ON SYNTHETIC DATA" docstring warnings and the
     stderr warning prints, since they will no longer be true.
   - Remove (or flip to `"synthetic": False`) the `carbonatix_provenance`
     attribute assignment described above, so the real-data artifacts do
     not carry a pickled claim of being synthetic.
4. Re-run both training scripts to produce real artifacts, and commit
   `nickel_lme.pkl` and `idx_carbon.pkl` in place of the `_SYNTHETIC`
   ones. Delete the `_SYNTHETIC` artifacts and CSV once the real versions
   are trusted and in place.
5. Update whatever in Task 11 (the serving path) references the
   `_SYNTHETIC` filenames to reference the real ones instead.
6. Only then, run the backtest described above and record the MAPE.
7. Delete or rewrite this file's "Status" line at the top once no
   synthetic artifact remains in the repo.
